# 마케팅 분석 — 수학·심리학·사회학 (2026-07)

코드베이스(랭킹 SQL·매처·프론트·발굴 파이프라인) 직접 확인 기준.
감상이 아니라 실제 구현된 메커니즘에 대한 진단이며, 각 항목에 근거 파일을 명시한다.

## 1. 수학적 시선 — 랭킹의 구조가 곧 제품의 성격

### 잘 만든 것: rank aggregation의 강건성 (`db/ranking.sql`)
- 소스별 순위의 평균(Borda 계열). value(네이버)와 count(댓글)는 단위가 달라
  직접 합산 불가 → 순위는 무차원이라 비교 가능.
- 순위는 단조변환에 불변 → 한 소스 어뷰징이 그 소스 1등 이상의 영향 불가.
  **어뷰징 내성이 구조적.** 소스 하나가 죽어도 나머지로 계산(격리 원칙).

### 구조적 결함 3개
1. **적분 vs 미분** — value 소스는 최근 7일 필터가 있으나 count 소스
   (`ranking.sql` 1번 뷰의 `count(*) filter (where value is null)`)는 시간 필터가 없다.
   댓글 언급이 전 기간 누적 → 순위가 "지금 뜨는 것"이 아니라 "역사상 많이 언급된 것"으로
   수렴. 오래된 밈이 구조적으로 상위 고정, 신상 밈이 치고 올라올 수 없다.
   트렌드 감지는 속도(Δmentions/Δt) 또는 시간감쇠 가중이 필요.
2. **저커버리지 편향** — 정렬이 `avg_rank asc` 우선, `source_count`는 동점 처리용
   (`ranking.sql` 3번 뷰). 마이너 소스 1곳에서만 1등인 밈이 5개 소스 전부 2등인 밈을
   이긴다. 참여 소스 수 기반 보정(베이지안 축소, 미참여 소스 패널티 순위 등) 필요.
3. **재현율 상한 = 사전 크기** — 사전 대조(`src/matcher.js`)는 정밀도 100%·노이즈 0이지만
   미등록 밈은 존재 자체가 안 잡힌다. scout(`src/naver/scout.js`)의 "밈 정리글 낚기"는
   이미 뜬 뒤의 후행 지표 → 감지 지연 = 밈 발생→정리글→운영자 검수의 합.

> 종합: 현재 수식은 "밈 **아카이브**의 수학"이지 "밈 **레이더**의 수학"이 아니다.
> 결함이자 포지셔닝 힌트(§4).

## 2. 심리학적 시선 — 심리 훅은 이미 3개 들어있다

| 훅 | 위치 | 메커니즘 |
| --- | --- | --- |
| 스와이프 덱 | `public/app.js` deckSection/attachDeck | 가변 보상(다음 카드 기대) + 카운터 "3/12"의 자이가르닉 효과. **가장 잘 설계된 부분** |
| "지금도 웃겨?" 투표 | `app.js` vote, `db/schema.sql` meme_votes | ①판정 권력(밈 사형선고 = cringe 문화의 쾌락) ②투표 직후 % 공개 = 사회적 비교 ③클릭 1번·로그인 불요 = 초저마찰 |
| 사회적 증거 | `app.js` metaSteady 등 | "N개 소스 측정"·"N표 참여"·댓글 수 = 신뢰 신호 |

### 빠져 있는 훅 (기회)
- **손실 프레임/FOMO 부재** — 진짜 지불 동기는 "나만 모르는 공포"인데
  "이번 주 놓친 밈 N개" 같은 손실 프레임이 UI에 없다. 마스트헤드 카피
  ("있는 그대로 보여드립니다")는 중립 관찰자 톤 — 신뢰엔 좋지만 전환엔 약함.
- **투표 후 정체성 보상 부재** — "상위 12%만 아는 밈" 같은 자기규정 피드백이 없어
  공유 동기로 이어지지 않는다.

## 3. 사회학적 시선 — 진짜 차별점

1. **소스 구성 = 사회학적 표본 설계.** dcinside·fmkorea(남초)·instiz·yeosig(여초)·
   youtube·naver(범대중). 한국 커뮤니티는 성별·성향으로 분절 → 밈이 경계를 넘을 때
   주류화된다. 따라서 `source_count`는 사실상 **"하위문화 경계 돌파 횟수" = 확산 폭**
   (Rogers 확산이론). 이걸 보여주는 서비스는 없다 = 방어 가능한 차별점.
   현재 UI는 이 귀한 데이터를 "N개 소스 측정"이라는 각주로만 쓴다.
2. **밈 = Social Currency** (Berger, STEPPS). 사용 맥락은 브라우징이 아니라
   "단톡 전 예습"과 "방금 들은 밈 뜻 검색". 후자가 획득 채널 문제로 직결(§4).
3. **"밈의 부고" = 사회적 의례.** "지금도 웃겨?" 시계열이 쌓이면 밈 사망 선고가
   가능해진다. 판정 기관 포지션은 언론 인용을 부르고, `mention_counts` 시계열은
   시간이 쌓일수록 못 베끼는 해자.

## 4. 종합 진단 — 치명 문제와 처방

| # | 문제 | 근거 | 처방 |
| --- | --- | --- | --- |
| 1 | **이름이 3개** — "밈 레이더"(package.json, server.js 로그) vs "밈 사전"(index.html title) vs "memedics"(app.js 상단바) | 레이더(속보)와 사전(권위·아카이브)은 다른 약속. 수식은 사전 쪽 | ✅ 해결(2026-07-14): **memedics 단일**로 통일. "밈 사전"은 매칭용 사전 데이터를 가리키는 기술 용어로만 유지 |
| 2 | **획득 채널 잠김** — SPA + 전 경로 index.html fallback(`server.js` SPA fallback)이라 밈별 URL·OG·색인 불가 | 자연 수요 = "○○ 뜻" 검색인데 검색에 안 잡힘. `docs/architecture.md`도 자인 | architecture.md Phase 2(상세 페이지 SSR/SEO)가 마케팅 최우선 |
| 3 | **바이럴 루프 0개** — app.js에 공유 버튼·공유 이미지 없음 | 투표 결과("예 34%")가 공유 욕구 정점인데 내밀 카드가 없음 | ✅ 해결(2026-07-14): `public/share.js` 캔버스 카드(생존 게이지+"당신의 판정은?" CTA) + Web Share/다운로드 폴백 + `#m=id` 딥링크 착지. 투표 카피도 생사판정([살았다]/[죽었다], 생존/사망%)으로 전환 |

| 5 | **랭킹 수식 결함** (§1의 1·2번) | count 소스 무기한 누적 + 저커버리지 편향 | count 소스 시간창(7일) 정합 + 커버리지 보정 |

### 한 줄 결론
팔 것은 "밈 모음"이 아니라 **"측정의 권위"**다. 수학(강건성·격리)과 심리 훅
(스와이프·심판 투표)은 이미 설계돼 있다. 없는 것은 ①이름 하나 ②검색 색인 ③공유 루프 —
전부 제품 내부가 아니라 **유통의 문제**이고, architecture.md의 SvelteKit 이전 위에서
해결 가능하다.

## 5. 실행 로드맵 (우선순위)

1. ✅ **랭킹 수식 수정** — count 소스 7일 창 + 백분위 축소(score, K=2). 라이브 적용됨. (§4-5)
2. ✅ **이름 통일** — memedics 단일로 확정·치환 완료. (§4-1)
3. ✅ **투표 신뢰 보강** — 표기 조정 + DB 트리거 레이트리밋(잔여: IP 기반은 SSR 이전 시). (§4-4)
4. ✅ **공유 루프** — 투표 결과 공유 카드 + 생사판정 카피 + 딥링크. (§4-3)
5. ✅ **SEO/SSR** — SvelteKit(adapter-vercel) 이전 Phase 1~2 구현(2026-07-15).
   `/`(순위·목록 SSR) + `/m/[id]`(상세 SSR — title "○○ 뜻", OG, canonical) +
   sitemap.xml/robots.txt + 구 해시 링크(#m=) 리다이렉트 + 투표·댓글·공유 카드 포팅.
   레거시 admin/withdraw는 static/으로 병행. **배포 스왑은 대기**: vercel.json이
   아직 구 정적 사이트를 가리킴(스트랭글러 — 스왑 전 파리티 확인: 스와이프 덱 미포팅). (§4-2)
6. ✅ **판정 시계열 1단계** — 1표 영구제가 게이지를 전성기에 화석화하는 문제 해결.
   `db/votes_lifecycle.sql`: PK에 month_bucket 추가(월 1회 재판정, 번복 역사 보존 =
   사망 곡선 데이터), 게이지는 최근 90일 내 투표자별 최신 판정만. 프론트 월 쿨다운
   ("지난 판정: 살았다 · 다시 판정 가능").
7. ✅ **판정 시계열 2단계** — steady→dead 분기 구현(`db/death_lifecycle.sql`).
   death_candidates 뷰 = 기계 신호(30일 언급 0) × 인간 신호(90일 사망%≥70 + 10표↑),
   기각 시 60일 쿨다운. 관리자 "사망 검토" 탭에서 선고/기각(탄생도 죽음도 기계는
   제안, 사람이 결정). dead는 부고 구역에 전시(스테디 탭 하단 †), 상세에 사망 선고일,
   편집에서 status 되돌리면 부활(died_at 자동 해제). 재심 덱: 90일 표 10개 미만
   스테디 밈 무작위 3개를 스와이프 덱에 재소환("재심 · 살았나 죽었나" 배지).
   임계값(70%/10표/30·60일)은 데이터 쌓인 뒤 조정.
