# 순위 월드컵 — 설계서

> 이상형 **순위** 월드컵 웹앱. 둘씩 비교하거나 직접 드래그해서 **전체 순위**를 뽑고,
> 주제를 링크로 공유하며, 여러 유저의 결과를 **집계**한다.

- **문서 상태**: 초안 v1 (2026-07-07)
- **범위**: 집계형 — 공유 + 결과 집계 + (선택적) 기기 간 동기화. **로그인 UI 없음**(접근성 우선, §5 익명 세션).

---

## 1. 목표 & 비목표

### 목표
- 이상형 월드컵 UX(둘 중 하나 고르기)를 유지하되, **1등만이 아니라 전체 순위**를 산출한다.
- 순위를 얻는 **3가지 경로**를 제공한다: 월드컵(대결) · 정렬(인터랙티브 병합 정렬) · 직접(드래그).
- 사용자가 **후보를 이름 + 사진으로 직접 추가**해 나만의 주제를 처음부터 구성한다(정해진 후보 풀 없음).
- **새 주제 생성도 관리자 승인이 필요**하다. 만들면 바로 공개가 아니라 **대기(pending)** 로 들어가고, 관리자가 승인해야 공개된다(거절 시 게시 안 됨).
- **승인되면 그 주제는 더 이상 작성자의 것이 아니다.** 원 작성자도 승인 후에는 **수정·삭제할 수 없고**, 이후 변경은 관리자만 하거나 일반 유저처럼 **제안**으로만 가능하다. (승인 전 대기 상태에서는 작성자가 자기 초안을 편집·삭제 가능)
- 승인된 주제는 **모두 공개**된다. 홈에서 **여러 주제를 둘러보고 골라서** 플레이하고, 링크로도 공유한다.
- **남의 주제에도 후보 추가·수정을 제안**할 수 있다. 단 즉시 반영이 아니라 **관리자 승인 시에만 반영**되고, 거절하면 제안은 취소된다(제안·승인 워크플로).
- **관리자는 모든 요청(주제 생성·후보 제안·신고)을 상세히 검토**한 뒤 승인/거절한다.
- 여러 명의 플레이 결과를 모아 **집계 통계**("전체 유저 1위")를 보여준다.
- 결과를 **PDF로 내보낸다**(기존 기능 계승).

### 비목표 (당분간 안 함)
- 실시간 대전/멀티플레이(동시 접속 대결).
- 댓글·좋아요 등 SNS 기능.
- 모바일 네이티브 앱(웹 반응형으로 충분).

## 3. 핵심 개념 — 순위를 뽑는 3가지 모드

### 3.1 월드컵 모드 (대결)
- 화면: 둘 중 하나 클릭. 기존 이상형 월드컵과 동일한 느낌.
- 순위 산출: **탈락 라운드 기반 등수**(8강 탈락=5~8위 …). 같은 라운드 탈락자는 공동 등수.
- 특징: 빠르고 익숙하지만 하위권 순위가 뭉툭함.

### 3.2 정렬 모드 (인터랙티브 병합 정렬) — 이 앱의 핵심
- 화면: 월드컵과 똑같이 "둘 중 누가 위?" 를 물어봄.
- 속: **병합 정렬(merge sort)의 비교 판단을 사람이 대신**한다.
  1. 항목을 둘씩 짝지어 각 쌍을 비교·정렬.
  2. 정렬된 묶음들을 맨 앞끼리 비교하며 병합.
  3. 전 항목이 하나의 정렬된 리스트가 될 때까지 반복.
- 비교 횟수: 약 `n·log₂(n)` (16개 ≈ 32회). 라운드로빈(120회)보다 훨씬 적음.
- **이미 아는 관계는 안 물어봄**(추이성: A>B, B>C ⇒ A>C 자동). 이게 효율의 핵심.
- 결과: **공동 등수 없는 완전한 1~N위**.

#### 엔진 인터페이스(초안)
```ts
// 화면과 완전히 분리된 순수 모듈. 비동기 비교 함수를 주입받는다.
type Compare<T> = (a: T, b: T) => Promise<-1 | 1>; // -1: a가 위, 1: b가 위

interface RankSession<T> {
  next(): { a: T; b: T } | null; // 다음에 물어볼 쌍, 없으면 종료
  answer(winner: T): void;        // 사용자 선택 반영
  progress(): { asked: number; estimatedTotal: number };
  result(): T[] | null;           // 완료 시 순위 배열
}
```
> 화면은 `next()`가 준 쌍을 보여주고, 클릭 결과를 `answer()`로 넘기기만 한다.
> 진행률 표시를 위해 `estimatedTotal`(≈ n·log₂n) 제공.

### 3.3 직접 모드 (드래그)
- 화면: 후보 리스트를 드래그해 순위를 직접 배치.
- 기존 `sortable.js` 로직 계승.

## 4. 데이터 모델 (Postgres / Supabase)

```
profiles      (id PK → auth.users, nickname, is_admin bool default false, created_at)
topics        (id PK, owner FK→profiles, title, description,
               default_mode ['worldcup'|'sort'|'drag'],
               status ['pending'|'active'|'hidden'|'rejected'] default 'pending',
                                                              -- 생성 시 pending, 승인 시 active(공개),
                                                              -- 신고 처리 시 hidden, 생성 거절 시 rejected
               cover_path, created_at)
candidates    (id PK, topic_id FK→topics, name, image_path, sort_order)
plays         (id PK, topic_id FK→topics, player FK→profiles NULL(익명 허용),
               mode, candidate_count int,   -- 플레이 시점의 후보 수(순위 정규화용 스냅샷)
               created_at)                  -- ★ TTL 임시(집계 원천). W/H 폴딩 후 프루닝 — 아래 집계 참조
play_ranks    (play_id FK→plays, candidate_id FK→candidates, rank int,
               PK(play_id, candidate_id))    -- ★ 동일: 폴딩 후 프루닝(개별 순위 영구저장 안 함)

-- ── 유계 집계(영구·정본). 후보 수 N 으로만 커지고 플레이 수와 무관(O(N²)) ──
pairwise_wins (topic_id, mode, winner_id FK→candidates, loser_id FK→candidates,
               wins bigint, PK(topic_id,mode,winner_id,loser_id))  -- 승리행렬 W. raw 정수, ε는 읽기 시
position_hist (topic_id, mode, candidate_id FK→candidates, position int, cnt bigint,
               PK(topic_id,mode,candidate_id,position))            -- 위치 히스토그램 H(실측 순위분포)
bt_strengths  (topic_id, mode, candidate_id FK→candidates, theta, updated_at)  -- BT/PL 강도 θ 캐시(W서 유도)
tribe_centroids (topic_id, k int, centroid jsonb, member_cnt bigint, PK(topic_id,k))  -- 온라인 k-means '부족'

reports       (id PK, topic_id FK→topics, reason text, reporter_hint text NULL,
               status ['open'|'resolved'] default 'open', created_at)
suggestions   (id PK, topic_id FK→topics, requester FK→profiles NULL(익명 허용),
               kind ['add'|'edit'|'delete'],
               target_candidate_id FK→candidates NULL,   -- edit/delete 대상
               proposed_name text NULL, proposed_image_path text NULL,
               status ['pending'|'approved'|'rejected'] default 'pending',
               reviewed_by FK→profiles NULL, reviewed_at, created_at)
```
> **새 주제는 `pending` 으로 생성**되고 관리자 승인 시 `active`(공개)가 된다. 거절은 `rejected`.
> 승인된 주제만 홈·검색·플레이에 노출된다. 신고로 문제된 주제는 `hidden`(소프트 삭제).
>
> **후보 직접 추가(생성 시)** 는 그 주제의 `candidates` 로 함께 심사되고, **남의 주제에 대한 제안**은
> `suggestions` 에 `pending` 으로 쌓였다가 **승인 시에만** `candidates` 에 반영된다.

### 집계 — 유계 충분통계 (W · H), 원본은 TTL

원본 순위(`play_ranks`)를 영구 저장하면 **O(플레이 수)로 무한 증가**(바이럴 한 주제가 무료 500MB를 위협). 대신 **플레이 저장 시 유계 집계로 폴딩하고 원본은 TTL 후 프루닝**한다. 공유는 순위를 URL에 인코딩(§7.5)하므로 원본 영구보관이 애초에 불필요.

두 집계가 이 게임 통계의 **충분통계**다(원본 순위를 버려도 무손실¹):
- **승리행렬 W** `pairwise_wins[i][j]` = i가 j를 이긴 횟수. Bradley–Terry/Plackett–Luce 강도 θ의 충분통계 → 평균 쌍대선호·Elo·**희귀도**(PL: P(π)=∏θ/Σθ³)까지 전부 파생.
- **위치 히스토그램 H** `position_hist[i][p]` = i가 p위였던 판 수 → "몇 %가 X를 1위로" 같은 **실측 순위분포**(W로는 못 구함, 모델 무가정).

두 왜곡 보정은 유지: **① 후보 수 정규화**(`plays.candidate_count` 스냅샷, `(rank-1)/(count-1)`; H를 정규화 위치로 담아 흡수) **② 모드별 분리**(W·H를 `mode`로 키잉 — 월드컵=공동등수, 정렬/드래그=유일등수).

```
θ(BT/PL 강도) = W 에서 Zermelo 반복으로 추정. ε 가상승패로 정규화(Ford 조건):
  어떤 후보가 한 번도 안 지면 MLE 발산 → 각 쌍에 ε 승·패 가산(= 가우시안 prior MAP²).
  raw W 는 ε 없이 저장, ε 는 추정 시점에만 적용(되돌릴 수 있음 — 원본 보존 원칙).
avg_norm(정규화 평균순위)·1위%·희귀도·부족은 전부 W·H·θ 에서 파생 — 원본 순위 불필요.
```

- 화면 "전체 1위" = θ 내림차순(또는 H의 avg_norm 오름차순). "나 vs 평균"·희귀도·부족은 W·H·θ 조회(read-only).
- **폴딩 경로:** MVP는 저장 시 `wins += 1` 직접 UPSERT. 트래픽 커지면 append-only 이벤트 → 크론 배치 폴딩 + 원본 프루닝(핫로우 회피). θ는 `bt_strengths`에 주기 캐시.
- 상세 수학(충분통계·ε·희귀도·k-means)과 무료티어 예산은 §4.1 참조.

### 이미지 저장 — Cloudflare R2 (egress $0)

- 유저 이미지 바이너리는 **Cloudflare R2** 버킷 `candidate-images`·`covers`. DB엔 **경로만**.
- **`image_path` 는 스토리지 base URL 없이 버킷 상대 경로로 저장**(예: `topics/{topic_id}/{content_hash}.webp`). 표시 시 `PUBLIC_STORAGE_BASE_URL` + path 조합 → **Supabase Storage(D2 임시) ↔ R2 이관이 환경변수 스위치 한 번**으로 끝남(대량 URL rewrite 불필요). 콘텐츠 해시로 재업로드·CDN 캐시 무효화 안전.
- **왜 Supabase Storage 아님:** Supabase Free egress 5GB/월 = 이미지 20KB 기준 **월 26만 뷰**서 초과 시 `restrict`(402·앱 다운). R2는 **egress 영구 $0**(월 1천만 뷰까지 무료), read-heavy 공유 앱엔 비용이 아니라 **가용성** 문제. → Supabase는 DB/Auth, 이미지 blob은 R2로 분리.
- 커스텀 도메인 붙이면 Cloudflare CDN이 자동 앞단(캐시 히트가 R2 읽기 ops까지 절감).
- 큐레이션(코드 내장) 이미지는 **Vercel 정적 CDN** `/gen/*.webp` 유지(무료 ~524만 뷰/월, SEO·prerender).

### 이미지 제한
- **주제당 최대 256강 = 후보 256명 = 이미지 최대 256장** (+ 주제 커버 1장 = 최대 257장).
- 월드컵 모드는 강 크기 2·4·8·…·256(2의 거듭제곱) 사용, 인원이 부족하면 부전승(bye) 처리.
- 정렬·직접 모드는 후보 수 제한 없이 최대 256까지 자유.
- 무료 티어 Storage(1GB) 보호를 위해 **업로드 시 클라이언트에서 리사이즈·압축**(예: 긴 변 512px, WebP)을 권장.

### 4.1 통계·인프라 심화 (검증판)

> 통계 명제는 논문, 인프라 수치는 공식 가격문서로 확인(각주). 목표: 플레이가 1억이어도 상태 유계.

**충분통계 격자 (주제당, N=후보 수).** 모든 모집단 기능이 유계 상태로 환원:

| 기능 | 최소 상태 | 크기 |
| --- | --- | --- |
| 평균 쌍대 "X>Y %" / Elo·BT 강도 (5-1) | W (승리행렬) | N² |
| "몇 %가 X를 1위로" | H (위치 히스토그램) | N² |
| 희귀도 "상위 3%" | θ로 logP(π) + t-digest 백분위 | N + bins |
| 취향 부족 (5-7) | 온라인 k-means 중심 k개 | k·N |
| 취향 쌍둥이 (5-3, 근사) | reservoir 샘플 m개 | m·N |
| 커플/친구 일치율 (5-2) | 두 순위 Kendall τ | 임시 |
| 지역·세대 (5-8) | W·H를 파티션별 | d·N² |

→ 주제당 영구 상태 ≈ O(d·N²), **플레이 수 무관.**

**k-means 부족 갱신:** 유저 벡터 `xᵢ=(N−1−2·rankᵢ)/(N−1)`(중심화 Borda; Euclidean²≈Spearman). `j*=argmin‖x−cⱼ‖²; c_{j*} += η(x−c_{j*})`, `η=max(1/n,0.02)`(드리프트 추종). 중심 좌표로 후보 정렬해 자동 명명("매운맛 급진파"). O(kN) 유계.⁵

**무료티어 예산 (검증):**

| 자원 | Supabase Free | R2 | Vercel Hobby |
| --- | --- | --- | --- |
| DB | 500MB | — | — |
| Storage | 1GB | 10GB 무료 | — |
| Egress | **5GB/월**(초과=402 restrict) | **$0 무제한** | 100GB/월(~524만뷰) |
| 인증 | 익명 포함, 50k MAU | — | — |

DB 무한증가 위험(개별 순위 O(plays))을 §7.5 URL 공유 + W/H 폴딩으로 제거 → 500MB 장기 충분. 비활성 1주 pause는 크론 헬스핑으로 회피.

**정직한 미해결(§10 반영):** PL은 IIA 가정이라 비이행성(순환 취향)과 충돌 → 모델기반 희귀도는 근사(실측은 H). 단일 θ 희귀도="전체 평균 대비"; 부족-상대 희귀도는 mixture-PL(후순위). 익명 집계="사람당" 아님(레이트리밋+"전체 플레이 중" 표기). N=256이면 W=65k셀/주제(유계지만 N² 비용).

## 7. 데이터 흐름 (요약)

1. **주제 생성**: `/create`에서 후보를 직접 추가(이름+사진, 7.1 참조) → 이미지 Storage 업로드 → `topics`(status=`pending`)/`candidates` insert → **관리자 승인 대기**. 작성자는 `/me`에서 "심사 중" 상태로 확인. 승인되면 `active`가 되어 공개·플레이 가능.
2. **플레이**: `/t/[id]/play` → 엔진이 쌍 제시 → 사용자 선택 → 완료 시 순위 확정.
3. **결과 저장·공유**: 완료 순위를 **URL 인코딩**(§7.5)으로 공유(DB 행 불필요) + `/t/[id]/result` 표시 + PDF. 집계용으로 W/H 폴딩(원본 `plays`/`play_ranks`는 TTL 후 프루닝).
4. **집계**: 저장 시 W(승리행렬)·H(위치 히스토그램)에 폴딩(정규화·모드별) → θ 캐시 → `/t/[id]/stats`("나 vs 평균"·희귀도·부족) 시각화.
5. **동기화(선택)**: 원하는 사용자만 나중에 이메일 연결(계정 승격)로 익명 신원을 정식 계정에 귀속 → 기기 간 공유. UI 노출 없음, 접근성 훼손 없음.

### 7.1 주제 만들기 — 후보 직접 추가 (핵심 기능)
- `/create` 화면에서 **후보를 사용자가 직접 하나씩 추가**한다. 미리 정해진 후보 목록은 없다.
- 후보 행 하나 = **이름(텍스트) + 사진**.
  - 사진 입력: **파일 업로드**(기본) 또는 **이미지 URL 붙여넣기**(선택).
  - 파일은 클라이언트에서 리사이즈·압축(예: 긴 변 512px, WebP) 후 Storage 업로드.
- UX 동작:
  - `[+ 후보 추가]` 버튼으로 행을 계속 늘림. **최대 256개**(초과 시 추가 버튼 비활성).
  - 각 행 **삭제**, 드래그로 **순서 변경** 가능(초기 표시 순서용, 게임 순위와 무관).
  - 이름·사진이 빈 후보는 저장 시 제외(에러로 알림, 조용히 버리지 않음).
- 저장: `topics` 1건(status=`pending`) + `candidates` N건 insert. 업로드 실패한 이미지는 사용자에게 표시하고 재시도.
- 최소 조건: 후보 **2개 이상**이어야 주제 생성 가능(대결이 성립).
- **생성 즉시 공개되지 않는다.** 관리자 승인(7.3) 전까지 대기, 작성자만 `/me`에서 미리 볼 수 있다.

### 7.2 남의 주제에 제안 · 승인 흐름
- **내 주제 & 아직 승인 전(pending)**: 작성자가 후보 추가·수정·삭제를 **즉시** 자기 초안에 반영(`candidates` 직접 수정).
- **승인된 주제(active)**: 원 작성자도 **직접 수정·삭제 불가**. 소유권이 사라졌으므로 남의 주제와 똑같이 **제안**으로만.
- **남의 주제(또는 승인된 내 주제)**: `/t/[id]` 에서 `[후보 추가/수정 제안]` → 이름·사진 입력 → `suggestions` 에 `pending` 으로 저장.
  - `kind='add'`: 새 후보 제안(이름+사진).
  - `kind='edit'`: 기존 후보 수정 제안(`target_candidate_id` + 바꿀 이름/사진).
  - `kind='delete'`: 기존 후보 삭제 제안.
- **관리자 검토**(`/admin`, 관리자만): 대기 목록에서
  - **승인** → 서버 함수 `apply_suggestion(id)` 가 종류에 맞게 `candidates` 반영 + `status='approved'`.
  - **거절** → `status='rejected'` 로 표시, `candidates` 변화 없음(요청 취소).
  - 반영은 권한 검사(관리자/소유자) 포함한 **Postgres 함수(RPC)로 원자적 처리** — RLS 우회 없이 안전하게.
- **알림**(선택): 새 제안이 들어오면 신고와 같은 방식으로 Brevo 이메일로 관리자에게 통지.
- 제안 제한: 후보 수는 승인 후에도 **주제당 최대 256** 유지(초과 제안은 승인 단계에서 거절).

### 7.3 관리자 검토 (모든 요청 상세 확인)
관리자는 `/admin`에서 **세 종류의 요청을 모두 상세히** 보고 승인/거절한다.

| 요청 종류 | 상세 화면에서 보는 것 | 승인 | 거절 |
| --- | --- | --- | --- |
| **주제 생성**(`topics` pending) | 제목·설명·모드 + **후보 전체(이름·사진) 미리보기** | `status='active'`(공개) | `status='rejected'` |
| **후보 제안**(`suggestions` pending) | 대상 주제 + **현재 후보 vs 제안 내용 비교**(add/edit/delete, 사진 포함) | `apply_suggestion()` 반영 | `status='rejected'` |
| **신고**(`reports` open) | 신고 사유 + 대상 주제·후보 내용 | 주제 `hidden` 처리 후 `resolved` | 무혐의 `resolved` |

- 각 항목은 **한눈 목록 + 클릭 시 상세 패널**. 이미지·후보 리스트까지 열어 확인 가능.
- 모든 승인/거절은 권한검사 포함 **서버 함수(RPC)** 로 원자 처리, 처리자·시각(`reviewed_by`/`reviewed_at`) 기록.
- 대기 건수 배지로 표시, 처리 후 목록에서 사라짐(상태로 필터).

### 7.4 신고 흐름 (Brevo 이메일)
- 주제/후보 화면의 **신고 버튼** → 사유 입력 → 프론트가 `POST /api/report`(SvelteKit 서버 엔드포인트) 호출.
- 서버 엔드포인트가:
  1. `reports` 테이블에 기록(추적용).
  2. **Brevo Transactional Email API**로 관리자에게 신고 메일 발송(주제 링크·사유 포함).
- **`BREVO_API_KEY` 는 서버 전용 환경변수**(프론트 노출 금지, `PUBLIC_` 접두사 안 씀).
- 관리자는 메일 확인 후 문제 주제를 `status='hidden'` 으로 내려 노출 차단(소프트 삭제).
- 스팸 방지: 동일 주제 반복 신고 rate-limit(간단히 IP/세션 기준), 추후 강화.

### 7.5 결과 공유 — 무상태 URL (DB 행 없음)

- 완료 순위 π는 순열 → 후보 인덱스를 base64url 인코딩(16후보 ≈ 22자). `/{lang}/r/{topicSlug}/{encoded}`.
- 서버 OG 엔드포인트가 encoded 디코드 → 후보 이름·이미지(주제 정의, 소량·캐시) + 집계(W/H/θ) 조회 → **결과 카드 이미지 렌더**. **DB 행 0 · TTL 0 · 영구 · 바이럴 안전**(개별 순위 영구저장 회피의 핵심).
- 카드 이미지 자체는 **클라 html2canvas 저장**(storage·egress 0), 링크 프리뷰만 서버 OG(satori/@vercel/og).
- "나 vs 평균"·희귀도는 렌더 시 aggregate read-only 조회.
- **구현 상태**: 코덱(`src/lib/share/rankingCodec.ts`)·공유 버튼·`/{lang}/r/[id]/[enc]` 읽기전용 라우트 완료. `[id]`는 slug(샘플, 어디서나) 또는 사용자 주제 id(만든 기기 한정, 크로스-기기는 단계2 이후). 서버 OG 카드는 미구현.

### 7.6 친구 방 · 서로 비교 (계정 없이) — *설계만, 미구현*

> 목표: **친구끼리 방을 만들어 같은 주제를 각자 매기고 서로 비교**. 회원가입 없음. 유료화 안전(유계).
> 결정(2026-07-09): **설계만 문서화**하고 구현은 보류. **샘플 주제 먼저**(사용자 주제는 후순위).

**"계정 없어도"의 의미** — 로그인/가입 없음. 두 방식 다 이를 만족한다:

- **A. 무서버 비교** (인프라 0, 즉시 가능): 각자 플레이 → 결과 코드(§7.5 코덱 재사용). 친구가 호스트에게 코드를 전달(외부 메신저) → 비교 페이지가 나란히·일치율·합의순위 렌더. 단점: 코드 수동 전달(진짜 "방" 느낌 약함).
- **B. 서버 방** (인프라 필요): **방 코드 + 닉네임**으로 참가(Supabase 익명 세션, §10 이미 확정). 자동 수집·**비동기 비교**(폴링·새로고침, 실시간 아님 — 아래 결정 A). 단점: Supabase(단계2) 필요, 사용자 주제까지면 R2 업로드(단계3)도.

**공통 심장 = 비교 코어** (순수·무인프라·A/B 둘 다 재사용). 같은 주제의 순위 N개 입력 →
| 출력 | 방법 | 담당 |
| --- | --- | --- |
| 나란히 순위 | 렌더 | 이 기능(UI) |
| **일치율** "너와 나 87%" | Kendall τ / Spearman | **5-2**(다른 세션) |
| **그룹 합의 순위** | Borda 또는 W→BT θ(§4) | **5-1**(다른 세션) |
| 논란 후보 | 위치 분산 큰 것(H, §4) | 이 기능 |
> ⚠️ 일치율·합의는 **5-1/5-2를 소비**한다(중복 구현 금지). 이 기능은 방 데이터흐름·UI·논란후보만 담당.

```
rooms(code PK, topic_kind, topic_ref, candidate_ids[], mode, member_cap, locked, created_at, expires_at)
      -- topic_kind='sample'|'user'(판별자, 보강#5). topic_ref=slug. candidate_ids=주제 후보 스냅샷(보강#1)
room_members(room_code FK, anon_id, nickname, ranking, submitted_at, PK(room_code,anon_id))
      -- ranking=인코딩 순열(§7.5 코덱, candidate_ids 스냅샷 기준). 미제출이면 null. 재제출=upsert(last-wins)
```
→ 주제당 상태 = O(멤버수·N). **TTL(14일) + 멤버 캡(30~50)** 으로 유계 → 무료티어 안전.

**주제 범위(확정):** 샘플 먼저 — `topic_ref`에 slug만 저장하면 모두가 `publicTopics`로 해석(이미지 업로드 불필요). 사용자 생성 주제는 정의+이미지를 서버/R2에 올려야 해(단계3) 후순위.

**흐름(B안):** 방 생성(호스트, 주제 선택 → 코드) → `/{lang}/room/{code}` 공유 → 참가(닉네임) → 각자 기존 엔진으로 플레이 → 완료 시 순위 제출 → 방 화면이 나란히·일치율·합의·논란 렌더.

**단계 계획:** A(무서버 비교 페이지, 코덱 재사용)로 착수하면 오늘 배포 가능하고 그 **비교 컴포넌트**가 B의 방 화면에 재사용된다(코드 수동수집 glue는 B에서 버려짐 — 보강#14). B는 인프라(단계2/3) 붙을 때. **현재는 설계만 확정, 구현 보류.**

#### 설계 스트레스 테스트 — 보강 (커질 때를 대비한 결함 점검)

*사용자 결정(2026-07-09): **A 비동기 · B 친구 소규모(캡) · C 수정가능(last-wins) · D 코드 입장**. 아래에 반영.*

**🔴 구조적 (만들기 전 반드시):**
1. **주제 스냅샷** — `ranking`은 후보 인덱스라, 방 사는 중 주제 후보가 바뀌면(관리자 편집·제안 승인) 인덱스가 어긋나 τ·합의·표시가 **조용히 오염**. → 방 생성 시 `candidate_ids[]`(순서+개수) 동결, 모든 디코드/비교는 라이브 주제가 아닌 스냅샷 기준. (§4 `candidate_count` 스냅샷과 동일 원리)
2. **규모 경계** — per-member 나란히+O(M²) 일치율은 소규모에서만 성립. **결정 B=친구 소규모 전용(멤버 캡)** 으로 이 문제를 캡으로 차단. 만약 공개·대규모로 확장하면 임계 초과 시 **§4 집계(W/H/θ)로 강등**하는 게 탈출구(현재는 범위 밖, escape hatch만 문서화).
3. **동기 vs 비동기** — **결정 A=비동기**. 웹소켓/Realtime 불필요 → 폴링·새로고침 + "N/M 제출됨" 상태. Realtime은 후속 폴리시(범위 밖). 복잡도·비용 대폭 감소.

**🟡 유지보수·확장:**
4. **5-1/5-2 소비 계약 동결** — 비교 코어가 쓸 시그니처를 지금 못박음: `kendallTau(a: string[], b: string[]): number`(일치율, **5-2 아직 미존재**), `consensus(rankings: string[][]): string[]`(합의). 현재 `eloRanker`(5-1)·`consistency`(5-4)는 있으나 τ·consensus는 없음 → 이 계약을 5-2 담당과 공유.
5. **`topic_kind` 판별자** — 지금 넣어두면(값='sample') 사용자 주제 지원이 마이그레이션 없이 추가만으로. `candidate_ids` 스냅샷(#1)과 함께 미래 대비.
6. **RLS 2단** — "멤버만 읽기"는 가입을 막음(닭-달걀). → **rooms: 코드로 읽기 허용(익명)** / **room_members: 동료 멤버만 읽기, 쓰기는 자기 행만**(`anon_id = auth.uid()`).
7. **play→방 제출 seam** — 현 `/t/[id]/play`는 로컬 전용. → play가 `?room=code`를 받고 완료 시 방에 upsert. 이 연결부를 B 착수 시 설계.
8. **TTL 프루닝** — 만료 방 삭제 주체 = 크론(§4.1 헬스핑 재사용) + 읽기 시 `expires_at > now()` 필터.
9. **합의 방법** — 작은 그룹(순위 <10개)은 BT θ가 노이즈 → **Borda(정규화 평균순위) 기본**, 데이터 충분할 때만 BT.

**🟢 정직한 한계(밝히고 완화):**
10. **익명 = Sybil** — 세션 여러 개로 표 쌓기 가능(§4.1도 인정). 친구 방은 무해. IP 레이트리밋 + 선택적 방 잠금.
11. **코드 난입** — **결정 D=코드 입장**. 6자+ 랜덤 base32로 무작위 추측 최소화, `locked` 컬럼으로 시작 후 잠금 옵션, 닉네임은 Svelte 자동 이스케이프(XSS 무해).
12. **무상태 불변식의 예외** — 방은 앱 **최초의 사용자별 상태 행**(§7.5는 무상태). 의도된 예외, TTL로 유계 유지.
13. **재제출** — **결정 C=수정 가능**. 멤버당 1행 upsert = last-wins.
14. **A안 정직성** — 재사용은 비교 **컴포넌트**뿐, 코드 수동수집 glue는 B에서 폐기.

## 8. 배포 & 이식성 (Vercel → Cloudflare)

- **1차: Vercel** — `@sveltejs/adapter-vercel`.
- **전환 계획**: 범위(트래픽/비용)가 커지면 `@sveltejs/adapter-cloudflare`로 **어댑터 교체 + 설정 변경**만으로 이동.
  - Supabase는 호스팅 독립적이라 **DB/스토리지/인증 코드는 그대로**.
  - 환경변수(`PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_ANON_KEY`)만 새 플랫폼에 재설정.
- 즉 **락인 없음**: 프론트 어댑터 한 겹만 갈아끼우면 됨.
- **이미지 blob은 처음부터 Cloudflare R2**(egress $0 — §4.1). Supabase Storage의 5GB egress 벽(월 26만 뷰)을 피하려는 게 아니라, 애초에 read-heavy 공유 앱의 가용성 전제. Supabase는 DB/Auth 전용.

### 9.1 단계 3 상세 계획 — 앱 ↔ Supabase 연동

> 목표(로드맵 완료 기준): **링크로 남이 내 주제를 플레이**. 사용자 주제를 DB로, 이미지는 스토리지로.
> 결정(2026-07-09): **D1 샘플 DB 이관(seed) · D2 이미지=Supabase Storage 임시 · D3 MVP 자동공개(active) · D4 서버·브라우저 Supabase 클라이언트 분리 · D5 `image_path`=버킷 상대 경로 · D6 후보 `stable_key`(멱등 seed 근거)**.

**현황(코드 매핑):** 샘플 34개 = 정적 `samples.ts`+SSR+i18n(`i18n/topics.ts`, en/zh 오버레이·후보명 번역 3개). 사용자 주제 = localStorage, 이미지 = base64 data URL(512px webp, `image.ts`). `storage.ts`가 교체 지점. 홈=SSR 카드+클라 오버레이, 상세=공개 SSR/사용자 클라 onMount. **후보 id 는 현재 `${slug}-${i}` 인덱스 결합**(`publicTopics.ts:28`) → 재-seed·samples.ts 편집 시 인덱스 시프트로 W/H 통계 오염 위험 → D6로 해소.

**D1이 부른 스키마 보강(번역 보존 + 멱등 seed):** topics 단일 title/description엔 로케일이 없음 → 샘플 en/zh 유실 방지 + 재-seed 안정성 위해:
- `alter table topics add column slug text unique;` (샘플 URL·번역키·seed upsert 키)
- `alter table topics add column i18n jsonb not null default '{}';` (`{en:{title,description}, zh:{...}}` 오버레이)
- `alter table candidates add column i18n jsonb not null default '{}';` (후보명 번역)
- `alter table candidates add column stable_key text;` (**D6**: 후보 안정 식별자. seed upsert 키·samples.ts 편집 이력 무관)
- `create unique index candidates_topic_stable_key on candidates(topic_id, stable_key) where stable_key is not null;` (멱등 seed 근거, 사용자 후보엔 부담 없음)
- 읽기: `title = i18n[locale]?.title ?? title` (현 `publicTopics.ts` 규칙 그대로 DB로).

**구현 순서:**
- **3-0 기반(SSR-안전 세션 · D4)** — `@supabase/supabase-js` + **`@supabase/ssr`** 설치. **클라이언트 분리 명시**: `src/lib/supabase.ts`(브라우저 전용) + `src/lib/server/supabase.ts`(서버 전용, 요청 쿠키 인지). **`src/hooks.server.ts` 에서 익명 세션 보장** — 첫 응답에 anon 세션 쿠키 세팅. 이유: `+page.server.ts`(홈·`/t/[id]`)가 `+layout.svelte` 보다 먼저 서버에서 실행되므로, 브라우저 레이아웃에서 세션을 만들면 첫 SSR 조회가 쿠키 없이 나가 RLS 대상으로 실패·빈 결과가 될 수 있음.
- **3-1 스키마 보강** — 위 slug / i18n / **stable_key + 부분 유니크 인덱스** 마이그레이션(apply_migration).
- **3-2 샘플 seed(멱등 · D6)** — `samples.ts` 각 후보에 **`stableKey` 필드 추가**(자유 문자열, 이름 변경·재정렬과 무관). `scripts/gen-seed` 는 **topics.slug** + **(candidates.topic_id, stable_key)** UPSERT — 재실행 안전, 후보 추가·이름수정·재정렬 시에도 id 불변. **인덱스 기반 후보 id(`${slug}-${i}`) 폐지**, DB uuid 사용(§7.5 URL 코덱은 후보 배열 순서 스냅샷 기반이라 영향 없음). `owner=null`, `status='active'`, `image_path`는 **D5 규약대로 상대 경로**(`gen/파일명.webp`).
- **3-3 어댑터 교체(핵심·최대 파급)** — `storage.ts`를 Supabase 쿼리로(**동기→비동기**). `getTopic`(slug 또는 uuid → DB, i18n 머지), `listUserTopics`(owner=uid), `saveTopic`(insert active), `deleteTopic`. **홈·상세 SSR은 3-0의 서버 클라**(요청 쿠키·RLS 인지), 브라우저 CSR·쓰기는 브라우저 클라. `publicTopics.ts` 의 모듈 레벨 `Map` 캐시는 TTL 캐시로 대체(서버리스 멀티 인스턴스 대비).
- **3-4 이미지(경로 규약 · D5)** — Storage 버킷 `candidate-images`(public read). **경로 규약: `topics/{topic_id}/{content_hash}.webp`** — 콘텐츠 해시라 재업로드·CDN 캐시 무효화 안전. RLS 업로드 정책: 경로 첫 세그먼트 = 자기가 소유한 `topic_id`(uid 노출 없음). `image.ts::uploadImage()` 는 **상대 경로만 반환**(DB 저장용, base URL 미포함). 표시 시 `imageUrl(path)` 헬퍼가 `PUBLIC_STORAGE_BASE_URL`+path 조합 → **R2 이관은 환경변수 스위치**(대량 URL rewrite 불필요, D2→R2 이관 비용 최소화).
- **3-5 배선/비동기 파급** — 홈(DB 카드), 상세·플레이·`/r` 비동기 `getTopic`, 이미지 표시부는 전부 `imageUrl()` 경유. **→ 이 시점에 사용자 주제 공유 링크가 크로스-기기 실동작(§7.5 완성).**
- **3-6 검증** — 익명 생성→타 브라우저 링크 플레이+이미지 로드+RLS. 샘플 SSR/SEO(후보까지 크롤) 유지. **재-seed 멱등성**(같은 samples.ts 재실행 시 no-op) + **후보 편집 시 stable_key 로 id 불변** 확인.

**범위 밖(다음 단계):** 모더레이션/관리자(/admin), 플레이→W/H 폴딩(단계 4), 방(§7.6), Storage→R2 이관(D5 덕에 환경변수 스위치).
**리스크:** ①동기→비동기 파급(호출부 다수) ②SSR이 DB 의존(TTL 캐시로 완화) ③seed 정확도(이미지 경로·번역 병렬배열, stable_key 로 완화) ④자동공개라 스팸/부적절 주제 노출(모더레이션 도입 전까지 감수 — 최소 anon uid 당 rate limit 후속과제).

- [x] **승인 시 소유권 소멸** — 주제가 승인되면 원 작성자도 수정·삭제 불가(더는 자기 것 아님). 승인 전 대기 상태에서만 작성자가 자기 초안 편집. 이후 변경은 관리자 또는 제안. 5·7.2 참조.
- [x] **남의 주제(및 승인된 내 주제)에 제안·승인** — 추가/수정/삭제를 **제안**(pending) → **관리자 승인 시 반영, 거절 시 취소**. 7.2 참조.
- [x] **집계 = 유계 충분통계(W·H)** — 원본 순위 영구저장 대신 승리행렬 W + 위치 히스토그램 H 로 폴딩(플레이 수 무관 O(N²)). 정규화(`candidate_count` 스냅샷)·모드별 분리 유지. §4 집계·§4.1 참조.
- [x] **결과 공유 = 무상태 URL** — 순위를 URL 인코딩, DB 행·TTL 없음(§7.5). raw `plays`/`play_ranks`는 폴딩용 TTL 원천.
- [x] **이미지 = Cloudflare R2** — egress $0(가용성 전제). Supabase는 DB/Auth. §4.1·§8.
- [x] **BT/PL 강도 θ = ε-정규화** — Ford 발산 방지(가상 승패=가우시안 prior), raw W는 ε 없이 저장(되돌림 가능). §4.1.
- [x] **안정 후보 id 선행** — W·H가 후보를 영구 참조 → 재정렬해도 통계 불변(`candidates.id`, `sort_order`와 분리). **샘플은 `stable_key` + slug 로 seed 멱등성 확보**(§9.1 D6).
- [x] **서버·브라우저 Supabase 클라이언트 분리** — `hooks.server.ts` + `@supabase/ssr` 로 SSR 첫 왕복에 익명 세션 쿠키 세팅. `src/lib/supabase.ts`(브라우저) vs `src/lib/server/supabase.ts`(서버) 물리 분리(§5·§9.1 D4).
- [x] **`image_path` = 버킷 상대 경로** — base URL 은 `PUBLIC_STORAGE_BASE_URL` 로 런타임 조합. Supabase Storage(임시)↔R2 이관이 환경변수 스위치 하나(§4·§9.1 D5).
- [x] **관리자가 모든 요청 상세 검토** — `/admin`에서 주제 생성·후보 제안·신고를 상세(후보·사진·비교)로 보고 승인/거절. 7.3 참조.
- [x] **관리자 = 사이트 운영자** (`profiles.is_admin`). 위 승인·검토 담당.
- [x] **관리자는 모든 월드컵을 직접 수정·삭제 가능** — 소유 무관, 승인 절차 없이 즉시 편집(관리자 전용 권한). 5장 참조.
- [x] **승인된 주제는 공개** — 홈에서 둘러보고 골라 플레이. 비공개 옵션 없음.
- [x] **신고 = Brevo 이메일** — 신고 버튼 → `/api/report` 서버 엔드포인트 → Brevo로 관리자 메일 + `reports` 기록 → 관리자가 `status='hidden'` 처리(7.1 참조).
- [x] **친구 방·서로 비교 = 계정 없이** — 회원가입 없음(무서버 코드 전달 또는 Supabase 익명 세션). 유계(TTL+멤버 캡). **샘플 주제 먼저.** 일치율(5-2)·합의(5-1)는 소비만. 스트레스 테스트 반영: **비동기 · 친구 소규모(캡) · 수정가능(last-wins) · 코드 입장** + 주제 스냅샷·RLS 2단·Borda 합의. 지금은 **설계만 확정, 구현 보류**. §7.6 참조.
