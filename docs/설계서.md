# 정하기 놀이터 — 설계서

> 이상형 **순위** 월드컵 웹앱. 둘씩 비교하거나 직접 드래그해서 **전체 순위**를 뽑고,
> 주제를 링크로 공유하며, 여러 유저의 결과를 **집계**한다.

- **문서 상태**: 초안 v1 (2026-07-07)
- **범위**: 집계형 — 공유 + 결과 집계 + 계정 로그인 + 여러 기기 동기화

---

## 1. 목표 & 비목표

### 목표
- 이상형 월드컵 UX(둘 중 하나 고르기)를 유지하되, **1등만이 아니라 전체 순위**를 산출한다.
- 순위를 얻는 **3가지 경로**를 제공한다: 월드컵(대결) · 정렬(인터랙티브 병합 정렬) · 직접(드래그).
- 사용자가 **후보를 이름 + 사진으로 직접 추가**해 나만의 주제를 처음부터 구성한다(정해진 후보 풀 없음).
- **새 주제 생성도 관리자 승인이 필요**하다. 만들면 바로 공개가 아니라 **대기(pending)** 로 들어가고, 관리자가 승인해야 공개된다(거절 시 게시 안 됨).
- **승인되면 그 주제는 더 이상 작성자의 것이 아니다.** 원 작성자도 승인 후에는 **수정·삭제할 수 없고**, 이후 변경은 관리자만 하거나 일반 유저처럼 **제안**으로만 가능하다. (승인 전 대기 상태에서는 작성자가 자기 초안을 편집·삭제 가능)
- 승인된 주제는 **모두 공개**된다. 홈에서 **여러 주제를 둘러보고 골라서** 플레이하고, 링크로도 공유한다.
- **남의 주제에도 후보 추가·수정을 제안**할 수 있다. 단 즉시 반영이 아니라 **관리자 승인 시에만 반영**되고, 거절하면 제안은 취소된다(제안·승인 워크플로).
- **관리자는 모든 요청(주제 생성·후보 제안·신고)을 상세히 검토**한 뒤 승인/거절한다.
- 여러 명의 플레이 결과를 모아 **집계 통계**("전체 유저 1위")를 보여준다.
- 결과를 **PDF로 내보낸다**(기존 기능 계승).

### 비목표 (당분간 안 함)
- 실시간 대전/멀티플레이(동시 접속 대결).
- 댓글·좋아요 등 SNS 기능.
- 모바일 네이티브 앱(웹 반응형으로 충분).

## 3. 핵심 개념 — 순위를 뽑는 3가지 모드

### 3.1 월드컵 모드 (대결)
- 화면: 둘 중 하나 클릭. 기존 이상형 월드컵과 동일한 느낌.
- 순위 산출: **탈락 라운드 기반 등수**(8강 탈락=5~8위 …). 같은 라운드 탈락자는 공동 등수.
- 특징: 빠르고 익숙하지만 하위권 순위가 뭉툭함.

### 3.2 정렬 모드 (인터랙티브 병합 정렬) — 이 앱의 핵심
- 화면: 월드컵과 똑같이 "둘 중 누가 위?" 를 물어봄.
- 속: **병합 정렬(merge sort)의 비교 판단을 사람이 대신**한다.
  1. 항목을 둘씩 짝지어 각 쌍을 비교·정렬.
  2. 정렬된 묶음들을 맨 앞끼리 비교하며 병합.
  3. 전 항목이 하나의 정렬된 리스트가 될 때까지 반복.
- 비교 횟수: 약 `n·log₂(n)` (16개 ≈ 32회). 라운드로빈(120회)보다 훨씬 적음.
- **이미 아는 관계는 안 물어봄**(추이성: A>B, B>C ⇒ A>C 자동). 이게 효율의 핵심.
- 결과: **공동 등수 없는 완전한 1~N위**.

#### 엔진 인터페이스(초안)
```ts
// 화면과 완전히 분리된 순수 모듈. 비동기 비교 함수를 주입받는다.
type Compare<T> = (a: T, b: T) => Promise<-1 | 1>; // -1: a가 위, 1: b가 위

interface RankSession<T> {
  next(): { a: T; b: T } | null; // 다음에 물어볼 쌍, 없으면 종료
  answer(winner: T): void;        // 사용자 선택 반영
  progress(): { asked: number; estimatedTotal: number };
  result(): T[] | null;           // 완료 시 순위 배열
}
```
> 화면은 `next()`가 준 쌍을 보여주고, 클릭 결과를 `answer()`로 넘기기만 한다.
> 진행률 표시를 위해 `estimatedTotal`(≈ n·log₂n) 제공.

### 3.3 직접 모드 (드래그)
- 화면: 후보 리스트를 드래그해 순위를 직접 배치.
- 기존 `sortable.js` 로직 계승.

## 4. 데이터 모델 (Postgres / Supabase)

```
profiles      (id PK → auth.users, nickname, is_admin bool default false, created_at)
topics        (id PK, owner FK→profiles, title, description,
               default_mode ['worldcup'|'sort'|'drag'],
               status ['pending'|'active'|'hidden'|'rejected'] default 'pending',
                                                              -- 생성 시 pending, 승인 시 active(공개),
                                                              -- 신고 처리 시 hidden, 생성 거절 시 rejected
               cover_path, created_at)
candidates    (id PK, topic_id FK→topics, name, image_path, sort_order)
plays         (id PK, topic_id FK→topics, player FK→profiles NULL(익명 허용),
               mode, candidate_count int,   -- 플레이 시점의 후보 수(순위 정규화용 스냅샷)
               created_at)
play_ranks    (play_id FK→plays, candidate_id FK→candidates, rank int,
               PK(play_id, candidate_id))
reports       (id PK, topic_id FK→topics, reason text, reporter_hint text NULL,
               status ['open'|'resolved'] default 'open', created_at)
suggestions   (id PK, topic_id FK→topics, requester FK→profiles NULL(익명 허용),
               kind ['add'|'edit'|'delete'],
               target_candidate_id FK→candidates NULL,   -- edit/delete 대상
               proposed_name text NULL, proposed_image_path text NULL,
               status ['pending'|'approved'|'rejected'] default 'pending',
               reviewed_by FK→profiles NULL, reviewed_at, created_at)
```
> **새 주제는 `pending` 으로 생성**되고 관리자 승인 시 `active`(공개)가 된다. 거절은 `rejected`.
> 승인된 주제만 홈·검색·플레이에 노출된다. 신고로 문제된 주제는 `hidden`(소프트 삭제).
>
> **후보 직접 추가(생성 시)** 는 그 주제의 `candidates` 로 함께 심사되고, **남의 주제에 대한 제안**은
> `suggestions` 에 `pending` 으로 쌓였다가 **승인 시에만** `candidates` 에 반영된다.

### 집계 뷰 (정규화 · 모드별)
순위(`rank`)를 그냥 평균내면 두 가지 이유로 왜곡된다:
1. **후보 수가 시점마다 다름**(제안 승인으로 후보가 늘어남) → 4개 중 4위와 14개 중 4위가 같은 값.
2. **모드마다 순위 성질이 다름**(월드컵=공동 등수, 정렬/드래그=유일 등수).

그래서 **① 플레이 시점 후보 수로 정규화**하고 **② 모드별로 분리**해 집계한다.

```sql
-- 정규화 점수: 0(1위) ~ 1(꼴찌). 후보 수가 달라도 비교 가능.
-- normalized = (rank - 1) / (candidate_count - 1)
create view candidate_stats as
select
  c.topic_id,
  c.id                                          as candidate_id,
  c.name,
  p.mode,                                        -- 모드별로 분리 집계
  count(pr.*)                                    as play_count,
  avg( (pr.rank - 1)::numeric
       / nullif(p.candidate_count - 1, 0) )      as avg_norm,   -- 낮을수록 상위
  count(*) filter (where pr.rank = 1)            as wins        -- 1위 획득 횟수
from candidates c
join play_ranks pr on pr.candidate_id = c.id
join plays p       on p.id = pr.play_id
group by c.topic_id, c.id, c.name, p.mode;
```
- 화면의 "전체 1위"는 `avg_norm` 오름차순(정규화 상위)으로 뽑는다. 모드별 탭 또는 통합(정규화라 통합도 안전) 선택.
- 트래픽이 커지면 `materialized view` + 주기적 refresh로 전환.

### 이미지 저장
- Supabase Storage 버킷 `candidate-images`(후보), `covers`(주제 커버).
- DB에는 **경로만** 저장, 표시 시 public URL 또는 서명 URL 생성.

### 이미지 제한
- **주제당 최대 256강 = 후보 256명 = 이미지 최대 256장** (+ 주제 커버 1장 = 최대 257장).
- 월드컵 모드는 강 크기 2·4·8·…·256(2의 거듭제곱) 사용, 인원이 부족하면 부전승(bye) 처리.
- 정렬·직접 모드는 후보 수 제한 없이 최대 256까지 자유.
- 무료 티어 Storage(1GB) 보호를 위해 **업로드 시 클라이언트에서 리사이즈·압축**(예: 긴 변 512px, WebP)을 권장.

## 5. 보안 (RLS 정책 개요)

| 테이블 | 읽기 | 쓰기 |
| --- | --- | --- |
| topics | `status='active'` 는 누구나 / **본인 주제는 상태 무관 본인 조회**(대기 확인) / 관리자 전체 | 생성은 누구나(단 `pending` 고정) · **수정·삭제는 `본인 주제 AND status='pending'` 또는 관리자(모든 주제)** / 상태 변경은 관리자만 |
| candidates | 소속 topic 읽기 권한을 따름 | **`본인 주제 AND 그 topic이 pending` 또는 관리자(모든 주제) 직접 쓰기** (승인된 주제·남의 주제는 제안으로만) |
| plays | 누구나 읽기(집계용, 개인 식별 최소화) | **누구나 insert 가능**(익명 플레이) |
| play_ranks | plays 규칙을 따름 | plays 규칙을 따름 |
| profiles | 본인 + 공개 닉네임 | 본인만 |
| reports | 관리자만 읽기 | **누구나 insert 가능**(신고) / 상태 변경은 관리자만 |
| suggestions | 관리자 전체 / 본인 제안은 본인 조회 | **누구나 insert 가능(pending)** / 승인·거절은 관리자만 |

> **관리자(admin) 정의**: `profiles.is_admin = true` 인 계정. 신고·제안 승인 등 운영 권한.
> RLS와 승인 함수에서 `is_admin` 을 검사한다. 초기엔 운영자 계정 1개.
>
> **관리자는 모든 월드컵(주제)을 직접 수정·삭제할 수 있다.** 소유 여부와 무관하게 어떤 주제든
> 제목·설명·후보(이름·사진)를 **승인 절차 없이 즉시** 편집한다(운영/큐레이션 권한).
> 이 전면 수정권은 **관리자 전용**이며, 일반 유저는 남의 주제엔 여전히 **제안(7.2)만** 가능하다.

### 로그인 정책 — 익명 세션 (로그인 UI 없음)
- 사용자에게 **로그인 화면을 노출하지 않는다.** 첫 방문 시 Supabase **익명 로그인**으로 조용히 익명 계정을 발급한다.
- 이 익명 신원으로 **주제 소유권·수정권한**을 RLS로 보장한다(내 주제만 내가 수정/삭제).
- **플레이·주제 생성 모두 로그인 UI 없이 가능.** 이메일/비번 입력 없음.
- 원하면 나중에 이메일을 **연결(정식 계정 승격)** 해 기기 간 동기화를 켤 수 있다(선택).
- 한계: 앱 데이터 삭제·다른 기기에서는 익명 신원이 사라짐 → **기기 간 동기화는 계정 연결 시에만**.

원칙:
- 비밀키/서비스롤 키는 프론트에 절대 노출 금지. anon key만 사용, 나머지는 RLS로 방어.

## 7. 데이터 흐름 (요약)

1. **주제 생성**: `/create`에서 후보를 직접 추가(이름+사진, 7.1 참조) → 이미지 Storage 업로드 → `topics`(status=`pending`)/`candidates` insert → **관리자 승인 대기**. 작성자는 `/me`에서 "심사 중" 상태로 확인. 승인되면 `active`가 되어 공개·플레이 가능.
2. **플레이**: `/t/[id]/play` → 엔진이 쌍 제시 → 사용자 선택 → 완료 시 순위 확정.
3. **결과 저장**: `plays` + `play_ranks` insert(익명 가능) → `/t/[id]/result` 표시 → PDF 내보내기.
4. **집계**: 플레이 저장 시 `plays.candidate_count`(그 시점 후보 수)를 함께 기록 → `candidate_stats` 뷰(정규화·모드별) 조회 → `/t/[id]/stats` 시각화.
5. **동기화**: 로그인 시 내 주제·기록이 계정에 귀속되어 기기 간 공유.

### 7.1 주제 만들기 — 후보 직접 추가 (핵심 기능)
- `/create` 화면에서 **후보를 사용자가 직접 하나씩 추가**한다. 미리 정해진 후보 목록은 없다.
- 후보 행 하나 = **이름(텍스트) + 사진**.
  - 사진 입력: **파일 업로드**(기본) 또는 **이미지 URL 붙여넣기**(선택).
  - 파일은 클라이언트에서 리사이즈·압축(예: 긴 변 512px, WebP) 후 Storage 업로드.
- UX 동작:
  - `[+ 후보 추가]` 버튼으로 행을 계속 늘림. **최대 256개**(초과 시 추가 버튼 비활성).
  - 각 행 **삭제**, 드래그로 **순서 변경** 가능(초기 표시 순서용, 게임 순위와 무관).
  - 이름·사진이 빈 후보는 저장 시 제외(에러로 알림, 조용히 버리지 않음).
- 저장: `topics` 1건(status=`pending`) + `candidates` N건 insert. 업로드 실패한 이미지는 사용자에게 표시하고 재시도.
- 최소 조건: 후보 **2개 이상**이어야 주제 생성 가능(대결이 성립).
- **생성 즉시 공개되지 않는다.** 관리자 승인(7.3) 전까지 대기, 작성자만 `/me`에서 미리 볼 수 있다.

### 7.2 남의 주제에 제안 · 승인 흐름
- **내 주제 & 아직 승인 전(pending)**: 작성자가 후보 추가·수정·삭제를 **즉시** 자기 초안에 반영(`candidates` 직접 수정).
- **승인된 주제(active)**: 원 작성자도 **직접 수정·삭제 불가**. 소유권이 사라졌으므로 남의 주제와 똑같이 **제안**으로만.
- **남의 주제(또는 승인된 내 주제)**: `/t/[id]` 에서 `[후보 추가/수정 제안]` → 이름·사진 입력 → `suggestions` 에 `pending` 으로 저장.
  - `kind='add'`: 새 후보 제안(이름+사진).
  - `kind='edit'`: 기존 후보 수정 제안(`target_candidate_id` + 바꿀 이름/사진).
  - `kind='delete'`: 기존 후보 삭제 제안.
- **관리자 검토**(`/admin`, 관리자만): 대기 목록에서
  - **승인** → 서버 함수 `apply_suggestion(id)` 가 종류에 맞게 `candidates` 반영 + `status='approved'`.
  - **거절** → `status='rejected'` 로 표시, `candidates` 변화 없음(요청 취소).
  - 반영은 권한 검사(관리자/소유자) 포함한 **Postgres 함수(RPC)로 원자적 처리** — RLS 우회 없이 안전하게.
- **알림**(선택): 새 제안이 들어오면 신고와 같은 방식으로 Brevo 이메일로 관리자에게 통지.
- 제안 제한: 후보 수는 승인 후에도 **주제당 최대 256** 유지(초과 제안은 승인 단계에서 거절).

### 7.3 관리자 검토 (모든 요청 상세 확인)
관리자는 `/admin`에서 **세 종류의 요청을 모두 상세히** 보고 승인/거절한다.

| 요청 종류 | 상세 화면에서 보는 것 | 승인 | 거절 |
| --- | --- | --- | --- |
| **주제 생성**(`topics` pending) | 제목·설명·모드 + **후보 전체(이름·사진) 미리보기** | `status='active'`(공개) | `status='rejected'` |
| **후보 제안**(`suggestions` pending) | 대상 주제 + **현재 후보 vs 제안 내용 비교**(add/edit/delete, 사진 포함) | `apply_suggestion()` 반영 | `status='rejected'` |
| **신고**(`reports` open) | 신고 사유 + 대상 주제·후보 내용 | 주제 `hidden` 처리 후 `resolved` | 무혐의 `resolved` |

- 각 항목은 **한눈 목록 + 클릭 시 상세 패널**. 이미지·후보 리스트까지 열어 확인 가능.
- 모든 승인/거절은 권한검사 포함 **서버 함수(RPC)** 로 원자 처리, 처리자·시각(`reviewed_by`/`reviewed_at`) 기록.
- 대기 건수 배지로 표시, 처리 후 목록에서 사라짐(상태로 필터).

### 7.4 신고 흐름 (Brevo 이메일)
- 주제/후보 화면의 **신고 버튼** → 사유 입력 → 프론트가 `POST /api/report`(SvelteKit 서버 엔드포인트) 호출.
- 서버 엔드포인트가:
  1. `reports` 테이블에 기록(추적용).
  2. **Brevo Transactional Email API**로 관리자에게 신고 메일 발송(주제 링크·사유 포함).
- **`BREVO_API_KEY` 는 서버 전용 환경변수**(프론트 노출 금지, `PUBLIC_` 접두사 안 씀).
- 관리자는 메일 확인 후 문제 주제를 `status='hidden'` 으로 내려 노출 차단(소프트 삭제).
- 스팸 방지: 동일 주제 반복 신고 rate-limit(간단히 IP/세션 기준), 추후 강화.

## 8. 배포 & 이식성 (Vercel → Cloudflare)

- **1차: Vercel** — `@sveltejs/adapter-vercel`.
- **전환 계획**: 범위(트래픽/비용)가 커지면 `@sveltejs/adapter-cloudflare`로 **어댑터 교체 + 설정 변경**만으로 이동.
  - Supabase는 호스팅 독립적이라 **DB/스토리지/인증 코드는 그대로**.
  - 환경변수(`PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_ANON_KEY`)만 새 플랫폼에 재설정.
- 즉 **락인 없음**: 프론트 어댑터 한 겹만 갈아끼우면 됨.

## 9. 단계별 로드맵

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| **1** | SvelteKit 뼈대 + 순위 엔진(병합정렬·드래그·월드컵) 이식, localStorage 저장 | 로그인 없이 로컬에서 순위 뽑기·PDF 동작 |
| **2** | Supabase 프로젝트 생성 + 스키마 + Storage + RLS | 콘솔에서 테이블·정책·버킷 확인 |
| **3** | 로그인 + 주제 생성 + 이미지 업로드 + 공유 링크 | 링크로 남이 내 주제 플레이 가능 |
| **4** | 결과 저장 + 집계 통계 화면 | `/t/[id]/stats`에서 전체 1위 확인 |
| **5** | Vercel 배포 + private 레포 정리·커밋 | 공개 URL에서 동작 |

> 각 단계 끝에 실제 동작을 확인하고 보고한다(테스트 통과만으로 완료 처리하지 않음).

## 10. 결정 사항 / 미해결

### 확정됨
- [x] **로그인 UI 없음** — Supabase 익명 세션으로 처리(5장).
- [x] **익명 플레이 결과도 집계에 포함** — 참여량 확보 우선.
- [x] **이미지 제한: 주제당 최대 256강(256장) + 커버 1장** (4장 이미지 제한 참조).

- [x] **후보 직접 추가** — `/create`에서 이름+사진으로 후보를 직접 하나씩 추가(최대 256, 사진은 업로드/URL). 7.1 참조.
- [x] **새 주제 생성도 관리자 승인 필요** — 생성 시 `pending`, 승인돼야 공개(거절 시 게시 안 됨). 7.1 참조.
- [x] **승인 시 소유권 소멸** — 주제가 승인되면 원 작성자도 수정·삭제 불가(더는 자기 것 아님). 승인 전 대기 상태에서만 작성자가 자기 초안 편집. 이후 변경은 관리자 또는 제안. 5·7.2 참조.
- [x] **남의 주제(및 승인된 내 주제)에 제안·승인** — 추가/수정/삭제를 **제안**(pending) → **관리자 승인 시 반영, 거절 시 취소**. 7.2 참조.
- [x] **집계 정규화** — `plays.candidate_count` 스냅샷 + `(rank-1)/(count-1)` 정규화 + **모드별 분리**로 순위 왜곡 제거(후보 수 변동·공동등수 문제 해결). 4장 집계 뷰 참조.
- [x] **관리자가 모든 요청 상세 검토** — `/admin`에서 주제 생성·후보 제안·신고를 상세(후보·사진·비교)로 보고 승인/거절. 7.3 참조.
- [x] **관리자 = 사이트 운영자** (`profiles.is_admin`). 위 승인·검토 담당.
- [x] **관리자는 모든 월드컵을 직접 수정·삭제 가능** — 소유 무관, 승인 절차 없이 즉시 편집(관리자 전용 권한). 5장 참조.
- [x] **승인된 주제는 공개** — 홈에서 둘러보고 골라 플레이. 비공개 옵션 없음.
- [x] **신고 = Brevo 이메일** — 신고 버튼 → `/api/report` 서버 엔드포인트 → Brevo로 관리자 메일 + `reports` 기록 → 관리자가 `status='hidden'` 처리(7.1 참조).

### 미해결
- [ ] 관리자 신고·제안 알림 이메일 주소 지정(Brevo 발신·수신).
- [ ] 원 작성자(주제 소유자)에게도 자기 주제 제안 승인권을 줄지(현재는 사이트 관리자만).
- [ ] 정식 계정 승격(이메일/구글 연결) UI를 언제 붙일지.
- [ ] 신고·제안 rate-limit 구체 기준.
- [ ] 업로드 리사이즈 스펙 확정(긴 변 px·포맷).
- [ ] **모든 주제가 승인 대기 → 관리자 처리 부담**. 주제 폭증 시 대응(신뢰 유저 자동승인, 공동 관리자 등).
